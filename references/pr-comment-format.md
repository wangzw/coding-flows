# PR comment format discipline

PR comments are read by humans and acted on by the Coder. They are **not** a
log for the Reviewer agent's runtime state. Treat every byte you publish as
something a sleep-deprived maintainer will scroll past in two seconds.

This page enumerates what the skill may post, what it must never post, and
the format constraints for each allowed kind.

## Hard rules

1. **Length budget**: ≤ 25 visible lines per comment. Anything longer is
   split, collapsed in `<details>`, or moved to inline review comments.
2. **Machine markers** always go in HTML comments (`<!-- ... -->`).
   GitHub does not render them; humans don't see them.
3. **One `/lgtm` per reviewer per head SHA.** Re-LGTM only after a new
   commit pushes a new head SHA.
4. **No status-update comments.** "Re-reviewing after new commits", "plan
   v=2", "verdicts filled", etc. are forbidden. The Reviewer's working
   plan is local; the PR sees only outcomes.
5. **Never dump JSON/YAML/large data structures** into a comment. If a
   reader has to parse syntax to find the actionable insight, you've
   failed the audience.
6. **Code samples use fenced blocks** (```` ``` ````); prose does not.
7. **No emojis** unless the human user explicitly requests them.
8. **No agent attribution trailers** (`Co-Authored-By:`, "Generated by …").

## What the skill is allowed to post

### 1. `/lgtm` comment

Posted from the Reviewer cycle when every plan row passes. Exactly one per
reviewer per head SHA.

```
/lgtm

<!-- coding-flows:lgtm sha=<full-head-sha> reviewer=<reviewer-id> acs=AC-1,AC-2 invariants=name1,name2 -->
<1-3 sentences naming what was verified — specific test files, specific
invariants, any caveats.>
```

Constraints:

- Visible body: 1-3 sentences, ≤ 6 lines. Name AC IDs by ID; name
  invariants by ID; reference specific files when claim is non-obvious.
- HTML marker is one line. All four fields required.
- No headers, no bullet lists in the visible body (the marker is the
  machine-readable structure; the body is human prose).

### 2. `--request-changes` review body

Posted via `gh pr review --request-changes` when any plan verdict is `gap`
or `violation`, or any unstructured finding blocks approval.

Body format:

```
<1-2 sentence summary of what blocks /lgtm.>

- <file:line> — <finding in 1-2 sentences> — <suggested fix in 1 sentence>
- <file:line> — ...

[Optional: <details> block for context that's helpful but not the
 actionable spine. Use sparingly.]
```

Constraints:

- Total body ≤ 25 visible lines. Use inline comments (next section) for
  spot-specific items if the count grows.
- Each bullet anchors to a `file:line` reference and proposes a fix. A
  bullet without a fix proposal is incomplete.
- Use prose; do **not** translate the local review plan's JSON into a
  comment. Prose is the medium.
- Wrap deeply contextual material in `<details><summary>...</summary>`
  blocks so the actionable spine stays scannable.

### 3. Inline review comments

Posted via `gh pr review --comment` with line anchors, for spot-specific
findings:

```
gh api repos/<owner>/<repo>/pulls/<PR>/comments \
  -F body="<one-paragraph finding + suggested fix>" \
  -F commit_id=<head-sha> \
  -F path=<file> \
  -F line=<N> -F side=RIGHT
```

Constraints:

- Each inline comment is one paragraph, ≤ 6 lines.
- Suggest a fix or ask a precise question. Avoid "consider …" vagueness.
- For multi-line spans, set `start_line` + `line`.

### 4. `needs-human` marker comment

Posted from the notification protocol. First line is an HTML comment
serving as a dedupe key; visible body is a short paragraph + reason.

```
<!-- coding-flows:human-needed reason=<reason-tag> -->
@<human_user> — coding-flows needs your input here.

reason: <reason-tag>
<one-paragraph: what was tried, what's blocking, what specific decision
 you need from the human>
```

Constraints:

- Total body ≤ 15 visible lines.
- One reason tag per marker. If multiple reasons → post multiple markers
  (the dedupe key differs).

### 5. Issue-side acknowledgment comments

Posted to the linked issue when the Coder opens a PR or after the PR
merges. One line each.

```
Opened #<PR> to address this — please review if the approach diverges.
Shipped in #<PR> — thanks!
```

Constraints: exactly one sentence. No marker. No metadata.

### 6. Issue clarification comment (Coder Phase A)

When the Coder finds an issue ambiguous, post a focused question. Body
format:

```
<1-2 sentence framing of what's clear / what isn't>

Specific ambiguities I need resolved before implementing:
- <ambiguity 1 + which interpretation you would default to>
- <ambiguity 2 + ...>

Could you clarify? Trigger `needs-human` if a decision is needed
asynchronously.
```

Constraints: ≤ 15 lines. Bullet each ambiguity; do not blend.

## What the skill must never post

- "Review plan v=1 (initial)"
- "Review plan v=2 (verdicts filled)" / "verdicts filled" / "audit
  complete" status comments
- Re-review status updates ("Re-reviewing after new push…")
- Bare JSON dumps in any visible context (use HTML markers for machine
  data; use prose for humans)
- Multiple `/lgtm` comments by the same reviewer on the same head SHA
  (edit the existing one only when adding caveats — do not stack)
- Comments that exist solely to record agent runtime state ("Started
  cycle at …", "Phase C complete", "Heartbeat")
- Auto-translated copies of the local review plan JSON
- Long discussion threads about decisions that belong in an ADR or
  design doc (link to those instead)

## Using `<details>` correctly

`<details>` is for **optional context**, not for hiding the spine. The
visible summary line must convey the actionable point on its own.

**Length budget per `<details>`**: ≤ 10 visible lines when expanded. If the
context needs more than 10 lines, the right place is a linked design doc /
ADR / runbook, not a PR comment. A long `<details>` block is still a long
comment — collapsing it shifts the scroll cost, not the comprehension cost.

Good:

```
- src/auth.go:42 — `GetUser` doesn't validate `userID > 0`; pass `-1` and
  it queries the DB with a sentinel. Suggested fix: early-return on
  non-positive input.
  <details><summary>Why this matters here</summary>

  This path is reachable from /v1/admin/impersonate without any other
  validation — the postgres driver returns row 0 for many tables under
  this query, leaking row 0 of the users table to the caller.

  </details>
```

Bad (the actionable insight is hidden):

```
- <details><summary>One concern about src/auth.go</summary>

  ... 40 lines of context with the actual finding buried at the bottom ...

  </details>
```

## Self-check before posting

Before any `gh pr comment` / `gh pr review` / `gh issue comment` call:

1. Is this comment **actionable** for a human or the Coder? If not, drop it.
2. Is the actionable point in the **first 3 visible lines**? If not, restructure.
3. Could a reader scan only the bullets / first lines and know what to do?
4. Is any byte beyond byte 2000 essential, or can it go in `<details>` or
   an inline comment?
5. If you removed the comment entirely, would the PR be worse off? If
   "not really" → drop it.
